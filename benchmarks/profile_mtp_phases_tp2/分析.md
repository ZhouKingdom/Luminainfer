# MTP 一轮耗时归因（TP2 C4，真实 27B）

测量脚本：`benchmarks/profile_mtp_phases.py`。同一常驻引擎、8 条输入分两个 cohort
（每条 64 输出 greedy）、完整预热后对第二 cohort 连续 12 步计时，第 2 步用
`torch.profiler` 取 rank 0 的 kernel 级分解。所有插桩 benchmark 本地，未改生产文件。

## 结论一句话

**瓶颈是验证（目标模型）的逐 token rowwise 前向，占一轮约 98%；其中 GEMM 占 61.7%、
逐行 norm/拷贝/门控占 25.4%。真正的「难算」部分——GDN 递归状态内核——只占 0.8%。**

投机没有净提速，不是投机算法本身，而是验证路径为了与单 token decode 逐位一致，
把每一个线性层都拆成单 token 行、每行一次独立 GEMM。普通（非 MTP）decode 本来就是
批量的，所以能跑到 C128 满负载 ~1778 tok/s；MTP 验证被 rowwise 拖到 C4 只有 ~34 tok/s。

## 一轮各阶段（12 步平均，单位 ms）

| 阶段 | wall | cuda | 占比 |
|---|---:|---:|---:|
| draft（4 请求各一次 MTP 草稿） | 4×6.24=24.9 | 24.8 | ~10% |
| verify（run_verification 目标前向+argmax） | 237.7 | 237.7 | ~98% |
| 快照/提交/接受（verify_batch_total−verify） | 3.9 | 3.9 | ~1.6% |
| 一轮合计 | ~241.6 | ~241.5 | 100% |

draft 每次约 6.2ms（4 请求 ≈ 25ms），快照/提交约 3.9ms，都不是主要矛盾；IPC/主机同步
被并进这几项，规模上不足以解释负收益。

## verify 前向 GPU kernel 分解（rank 0，单轮）

| 家族 | 时间 ms | 占比 |
|---|---:|---:|
| GEMM（cuBLAS） | 151.5 | 61.7% |
| elementwise（norm/拷贝/门控/残差） | 62.4 | 25.4% |
| NCCL all-reduce | 14.3 | 5.8% |
| 其它（gemv/dot/index 等） | 13.9 | 5.7% |
| GDN delta 递归内核 | 1.9 | 0.8% |
| conv1d | 1.6 | 0.7% |
| argmax | 0.06 | ~0% |

关键 kernel 数量（单轮）：

- `ampere_bf16_s16816gemm_*` 共约 **2900 次 launch**（1028 + 1420 + 14 + 384 + …）。
  8 行验证窗口 × ~352 个线性层 ≈ 2816，与之一致：**每层每 token 各一次独立 GEMM**。
- `direct_copy_kernel` **5584 次、17.6ms**：`x.split(1)` + `torch.cat` 的逐行拆装拷贝。
- `rsqrt/pow/mean`、`mul/add` 逐行 norm 与门控，累计数十 ms。

`_paged_attn_decode_kernel`（full attention）仅 2.1ms，GDN delta 仅 1.9ms——混合模型的
「递归状态」计算不是瓶颈。

## 根因与优化方向

`decode_equivalent` 数值路径（`zjhvllm/models/qwen3_5.py` 的 `Qwen3_5Linear`、
`Qwen3_5ParallelLinear`、`Qwen3_5RMSNorm`，以及 `GatedDeltaNet.forward` 的 decode 分支）
在 `x.shape[0] > 1` 时执行 `torch.cat([F.linear(row) for row in x.split(1)])`，把批量
逐行拆开。该路径只为保证 MTP 验证与单 token decode 逐位一致，代价是每 token 一次 M=1
GEMM（tensor core 利用率极低）加上海量拆装拷贝。

对比普通 decode（`run_model` 中非 MTP 分支不设 `decode_equivalent`），线性层是标准批量
`F.linear`，这才是其高吞吐的来源。

优化方向：**让验证走批量算术**（对齐 SGLang 的批量草稿/批量验证），把 ~2900 次 M=1 GEMM
合并为 ~350 次 M=8 批量 GEMM，并消除逐行拆装。预期显著降低 GEMM 与 elementwise 两项
（合计 87%）。代价是验证 logits 与单 token decode 出现 BF16 舍入差异，可能罕见改变
greedy argmax，需单独验收「同后端投机/非投机一致」与「新旧输出差异」。
